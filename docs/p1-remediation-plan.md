## P1.3 保存失败后恢复写入

- `flush()` 在调用时序列化当前状态并提交快照。每次写入返回自己的 Promise，失败时向当前调用方传递原始错误。队尾另外接收已处理失败的 Promise，后续提交仍按顺序写入。继续使用临时文件、`fsync` 和重命名覆盖。 [StoreService](../src/main/services/store.ts#L82) · [原子写入](../src/main/utils/atomicFile.ts#L8)
- 防抖回调显式处理拒绝并写主进程诊断日志，保留内存状态，供下一次修改或显式 `flush()` 保存。原子写失败时尽力删除本次临时文件，诊断及清理保留原始写入错误。
- **验收。** 首次重命名失败时，显式 `flush()` 返回该错误，已有磁盘文件仍可读取。随后修改并保存，重新读取 `store.json` 能得到新状态。交错修改和并发提交多个快照时，最终文件对应最后一次成功提交。防抖保存失败时没有未处理的 Promise 拒绝，后续保存成功。 [Store 回归用例位置](../src/main/services/store.test.ts)

## P1.1 同一环境从启动预检开始互斥

- `start()` 生成 `runId`，在首次 `await` 前同步检查并占用 `Map<envId, runId>`。占用覆盖上传计划、凭据读取、历史记录落盘、排队和执行，释放时核对持有人。独立的 `run:precheck` 仍用于获取预览。 [启动入口](../src/main/services/runner.ts#L144)
- `queued` 记录落盘成功后，再对 `active` 和队列公布本次运行并交给 `pump()`。日志写入器在开始执行时打开，启动失败无需处理空日志。预检、凭据读取或落盘抛错时按 `runId` 撤销已插入的历史记录，保留其他并发修改。如可能已有排队快照包含该记录，提交撤销后的快照，保留原始启动错误并记录撤销写入的异常。提交完成或启动失败后，由对应路径接管或释放锁。
- 排队取消、正常终止和异常终止统一按归属释放。终态落盘失败时报告保存错误，仍发布内存中的终态并释放环境锁和全局并发名额。 [执行调度](../src/main/services/runner.ts#L304) · [收尾流程](../src/main/services/runner.ts#L591)
- **验收。** 用可控 Promise 暂停第一个启动请求的预检或凭据读取，在同一环境发起第二个请求，断言只返回一个 `runId`、只写一条历史记录、只尝试一次 SSH，且执行结束前第三个请求仍被拒绝。分别模拟预检失败、凭据读取抛错和首次落盘失败，断言失败请求未执行、内存和恢复落盘后的历史没有残留，重试可启动。覆盖排队取消和终态落盘异常后的再次启动。 [执行器回归用例位置](../src/main/services/runner.test.ts)

## P1.2 备份后替换失败时保留原目标

- 把每个上传临时文件放到其最终目标的父目录，包括目录上传中的嵌套文件。上传后校验大小和目标类型，再进行同目录替换。远端路径使用 POSIX 路径处理和现有 shell 转义。 [上传文件流程](../src/main/services/upload.ts#L43) · [远端替换](../src/main/services/upload.ts#L231)
- `backup` 策略下，目标存在时优先为旧文件在同目录建立硬链接备份。远端文件系统或权限不允许创建硬链接时，把旧文件复制到同目录的独立临时文件，复制完成后再发布备份。两条路径都沿用 `.bak-yyyyMMdd-HHmmss` 命名，重名时递增序号，发布时拒绝覆盖已有备份。备份发布成功后才通过同目录重命名原子替换目标。目标不存在时直接安装。`overwrite` 策略直接使用同目录重命名。
- 替换失败时记录阶段、目标、临时文件和已生成的备份路径，保留旧目标及备份。若已发出替换请求但未收到远端结果，例如断连或超时，日志注明替换结果未知并附已知路径，供核对远端实际状态。替换请求仍可能在远端执行时，保留相关临时文件供核对。单文件替换成功后即移出清理清单。
- **验收。** 模拟备份成功、替换失败，确认原路径的文件内容仍是旧版本，备份可读取，日志包含阶段及路径，部署命令没有启动。覆盖备份名冲突、无法硬链接时的复制备份、复制失败、目标不存在、正常替换、嵌套目录，以及原有目录和符号链接检查。断连后客户端应报告结果未知，并在日志中保留已知的备份路径。 [上传器回归用例位置](../src/main/services/upload.test.ts)

## P1.4 更新服务器时按旧地址和引用清理指纹

- 在实际修改服务器配置时，先从现有对象复制旧 `host` 和 `port`，再更新地址。服务器配置成功落盘后，查询当前配置中是否仍有服务器引用旧 `(host, port)`，仅在最后一个引用移除时清理。`server:remove` 使用同一引用规则。引用检查紧靠指纹的内存删除，以覆盖配置在保存等待期间发生的变动。 [服务器更新与删除](../src/main/ipc/server.ts#L42) · [信任记录键](../src/main/services/knownHosts.ts#L29)
- `KnownHostsService` 的 `trust`、`touch`、`remove` 按快照提交顺序串行落盘，避免晚完成的旧快照覆盖已更新的记录。沿用主机与端口的精确匹配，账号和名称变化无需清理指纹。 [指纹写入](../src/main/services/knownHosts.ts#L37) · [SSH 指纹校验](../src/main/services/ssh.ts#L66)
- **验收。** 从已信任的 A 改到已信任的 B，B 原指纹仍有效。A 还有其他配置时保留其指纹，最后一个引用移除时才清理。覆盖仅改端口、仅改账号、删除共享地址配置、配置保存失败和保存期间另一配置引用 A。通过 IPC 入口断言结果，并重新读取持久化指纹文件复核。 [指纹服务回归用例位置](../src/main/services/knownHosts.test.ts)

## P1.5 SFTP 空闲超时覆盖整个上传阶段

| 等待阶段                                   | 截止时间及处理                                                                                                                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 打开 SFTP                                  | 从发起请求起使用 `uploadIdleTimeoutSec`。取消、断连或到期时立即结束本地等待。迟到的 SFTP 会话立即关闭。                                                                          |
| 目录检查和创建、文件大小校验、目标类型检查 | 每次 `lstat`、`mkdir`、`stat` 请求分别使用该阈值，对超时或取消主动结束等待。                                                                                                     |
| `fastPut` 文件传输                         | 使用同一空闲阈值，仅累计字节增加时续期。传输完成回调同样受截止时间约束，空文件收到成功回调即可进入校验。                                                                         |
| 远端备份与替换                             | 从请求 `exec` 前计时，覆盖通道建立和退出状态。复制备份期间通过 SFTP 观察临时备份大小，仅在字节数增长时续期，与前端上传进度独立。超时或取消时关闭相应通道，迟到的通道也立即关闭。 |
| 失败清理                                   | 复用尚可用的连接，建议给整段清理独立的 10 秒预算。只处理可确认由本次任务遗留的临时文件，保留最初的失败原因并记录未确认的路径。                                                   |

- 上传等待统一结算一次，移除计时器和取消监听，忽略迟到的结果与进度。保留首个终止原因，空闲到期映射为 `timeout`，用户取消映射为 `canceled`，SSH 断连映射为 `disconnected`，远端明确返回失败映射为 `failed`。取消或超时应直接结束本地等待，关闭 SFTP 或执行通道用于停止底层活动。清理预算从失败处理开始，用户触发的取消也走同一收尾流程。 [SFTP 入口](../src/main/services/ssh.ts#L313) · [上传执行](../src/main/services/runner.ts#L397) · [现有空闲计时](../src/main/services/upload.ts#L119)
- **验收。** 用可控计时器分别挂起打开 SFTP、目录操作、`fastPut`、大小校验、远端 `exec` 的通道建立和退出、失败清理，验证到期后在清理预算内进入终态。覆盖用户取消、SSH 断连、迟到回调、虚假重复进度和持续真实进度。用占满四个名额并另有一个排队任务的场景确认名额恢复，同时验证原环境可再次启动、部署命令未被调用、终态事件只发一次。 [上传超时设计](design.md#L457)
